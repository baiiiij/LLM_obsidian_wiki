# 华为昇腾 CANN 软件栈与编程模型调研笔记

## 1. CANN 是什么 & 版本演进

**CANN（Compute Architecture for Neural Networks）** 是华为针对 AI 场景的异构计算架构，向上支持 MindSpore / PyTorch / TensorFlow 等框架，向下服务昇腾 AI 处理器，定位相当于 CUDA 软件栈（cudart + 驱动 + cuDNN/cuBLAS + NCCL + 编译器）的整体打包。

**版本演进时间线**（官方产品公告与版本配套资料）：

## 2. CANN 架构分层（对照 CUDA 生态）

自上而下（来源：阿里云开发者社区 CANN 架构解析、hiascend 文档）：

| CANN 组件 | 作用 | CUDA 对照 |
|---|---|---|
| **AscendCL**（Ascend Computing Language） | 统一 C/C++ + Python 应用编程接口，提供 Device/Context/Stream/Event 管理、内存管理、模型加载执行、单算子执行、媒体数据处理 | CUDA Runtime API + Driver API 合体 |
| **GE（Graph Engine）图引擎** | 图编译、算子融合、图切分与调度、常量折叠、内存复用，将框架图编译为可在 NPU 执行的图 | TensorRT 图优化 + CUDA Graph 的部分职能 |
| **算子库**：内置算子包 **opp** + **AOL（Ascend Operator Library，aclnn 系列 API）** | 内置高性能算子（NN/Math/Transformer/CV），C++ 侧通过 `aclnn*` 单算子 API 调用 | cuBLAS / cuDNN / ATen native kernels |
| **HCCL**（Huawei Collective Communication Library） | 单机多卡/多机多卡集合通信，支持 AllReduce、Broadcast、AllGather、ReduceScatter、AllToAll 等原语，Ring/Mesh/HD 算法，走 HCCS（片间高速互联）/RoCE/PCIe 链路 | NCCL（+ NVLink/InfiniBand 传输层） |
| **Runtime（aclrt）** | 硬件资源管理、单算子加载执行、模型推理的运行时 | cudart（libcudart） |
| **Driver** | 设备驱动与固件，配套 HDK 版本（25.x/26.x），与 CANN 有配套矩阵 | NVIDIA kernel driver |
| **毕昇编译器（BiSheng Compiler）** | Host-Device 异构编译，针对昇腾微架构优化，提供二进制调试信息与工具链；基于 LLVM 体系 | nvcc / ptxas |
| **Ascend C** | 原生算子编程语言（C++ 超集），SPMD+SIMD 模型，屏蔽硬件差异 | CUDA C++ |
| 上层套件 | torch_npu、MindSpeed（训练加速）、MindIE（推理引擎）、MindStudio 工具链 | PyTorch CUDA backend / apex / TensorRT-LLM / Nsight |

## 3. Host/Device 编程模型（对照 CUDA Runtime）

AscendCL 的资源管理流程与 CUDA 几乎一一对应（来源：华为云博客 AscendCL 运行时管理、华为开发者论坛 Kernel Launch 教程）：

```c
aclInit(nullptr);                          // ≈ cudaFree(0) / 驱动初始化
aclrtSetDevice(0);                         // ≈ cudaSetDevice
aclrtCreateContext(&ctx, 0);               // ≈ cuCtxCreate（CUDA 中 context 隐式）
aclrtCreateStream(&stream);                // ≈ cudaStreamCreate
aclrtMalloc(&dev, size, ACL_MEM_MALLOC_HUGE_FIRST);  // ≈ cudaMalloc
aclrtMallocHost(&host, size);              // ≈ cudaMallocHost (pinned)
aclrtMemcpy(dst, size, src, size, ACL_MEMCPY_HOST_TO_DEVICE); // ≈ cudaMemcpy
aclrtCreateEvent(&event);                  // ≈ cudaEventCreate
aclrtSynchronizeStream(stream);            // ≈ cudaStreamSynchronize
```

- **Device/Context/Stream/Event**：语义与 CUDA 一致；区别是 Context 在 AscendCL 中**显式创建**（可多个 Context 绑定一个 Device），默认 Context 为隐式。
- **内存层次**：Host 内存 / Device 全局内存（GM，HBM）二分，无 cudaMallocManaged 等价物的主流用法；`ACL_MEM_MALLOC_HUGE_FIRST` 表示优先申请大页内存。
- **Kernel 下发**：Ascend C 算子用 `kernel_name<<<blockDim, l2ctrl, stream>>>(args)` 语法（或 `ACLRT_LAUNCH_KERNEL` 宏 / `aclrtLaunchKernel`），`blockDim` 指定使用的 AI Core 核数——这是与 CUDA grid/block 二维结构的重要差异。
- **执行模式**：**单算子模式**（aclnn API 逐算子下发，类似 PyTorch eager）与**图模式**（整图交给 GE 编译执行，训练/推理框架默认走图模式；torch_npu 的 ACLGraph/NPUGraph 是图捕获机制，对应 CUDA Graph）。
- 模型推理有更高层 API：`aclmdlLoadFromFile` 加载离线模型（.om 文件，由 ATC 工具从 ONNX/TensorFlow 图编译而来，类比 TensorRT engine）。

## 4. SPMD 编程模型 vs CUDA SIMT

这是与 CUDA 最本质的区别（来源：CANN 训练营对比笔记、GitCode Ascend C 编程指南、浙大 HPC101 实验文档）：

- **CUDA SIMT**：程序员以"单线程"视角写 kernel，硬件以 warp（32 线程）为单位锁步执行，靠海量线程隐藏延迟；并行度体现在 threadIdx/blockIdx 的细粒度索引上。
- **Ascend C SPMD（Single-Program Multiple-Data）**：并行度直接对应**物理 AI Core**。一份 kernel 同时运行在所有 AI Core 上，每个核的执行实例仅靠内置变量 `block_idx` 区分身份，各自处理被切分（tiling）后的数据分片。没有 warp/线程概念，一个核内是 SIMD 向量指令 + Cube 矩阵单元 + Scalar 单元三类物理单元并行执行。
- **多核切分**：Host 侧 tiling 函数根据输入 shape 计算每个核处理多少数据，block 数一般设为物理核数的整数倍。核内数据流是显式的三级流水：DMA 搬入 Global Memory → Local Memory（UB/L1/L0A/B/C）→ Vector/Cube 计算 → 写回。这更接近"手写数据流水"而非 CUDA 的缓存层次。
- 910B 系列采用 **AIC（Cube 核）/ AIV（Vector 核）分离架构**，通过片内总线通信。

一句话总结：CUDA 是"一个线程算一个元素"，Ascend C 是"一个核算一个数据分片，核内向量化+流水化"。

## 5. 框架对接现状（2025–2026）

**torch_npu**（gitee.com/ascend/pytorch）：
- 基于 PyTorch **PrivateUse1** 机制接入，重命名为 `npu`：`torch.npu.xxx`、`tensor.npu()`；分布式用 `ProcessGroupHCCL`（`dist.init_process_group(backend="hccl")`）。
- 提供自动迁移：`from torch_npu.contrib import transfer_to_npu` 拦截 `torch.cuda` 调用转发到 NPU。
- 版本与 CANN/PyTorch 严格配套。截至 2026-09 最新组合：CANN 9.1.x + torch_npu 26.1.1 产品线（pip 包名如 `torch_npu==2.12.0.post2`，支持到 PyTorch 2.12）。
- 执行后端可选 eager（aclnn 单算子）或图模式（torchair + GE）。

**vLLM-Ascend**（vllm-project/vllm-ascend，官方社区插件）：
- 2025-02-19 首版 v0.7.1rc1；v0.9.0（2025-06）起默认推荐 V1 引擎、V0 冻结；v0.10.x 支持 Qwen3-Next；v0.11.0（2025-12-16）支持 DeepSeek-V3.2；2026 年持续演进，已支持 Ascend 950 的 W8A8/W4A8 动态量化、MXFP8 MC2 dispatch/combine、ACLGraph、DeepSeek V4 融合算子等。文档站最新稳定版 v0.13.0。
- 提供自定义算子框架，允许用 Ascend C 给 vLLM 写 kernel。

**SGLang**：2025-07 起官方支持 Ascend NPU 后端（`--attention-backend ascend --device npu`），基于 torch_npu + **triton-ascend**（昇腾版 Triton，可 pip 安装），实现了 ACLGraph（NPU Graph 捕获）、W8A8 量化、MLA、DeepSeek/Qwen 系列支持、KV cache 集群传输、PD 分离；2026 Q1 roadmap 包括切换 CANN 8.5 stable、torchair compile 增强等。

|---|---|---|
| `npu-smi` | 设备信息、健康状态、功耗、固件升级（官方文档确认） | nvidia-smi |
| `msprof`（CANN Toolkit 自带，`tools/profiler/bin/msprof`） | 采集/解析/导出 profiling 数据（timeline、算子耗时、通信矩阵），输出可导入 chrome://tracing | nsys / nsight compute |
| `msprof-analyze`（pip 包，GitHub: Ascend/msprof-analyze） | 统计比对与瓶颈诊断，支持 GPU/NPU 性能差异对比、集群通信分析 | Nsight Systems 分析层 |
| MindStudio Insight | 可视化 timeline、通信分析 | Nsight GUI |
| `msNPUMon` | Prometheus exporter 式的 NPU 监控 ⚠️ 未在官方文档核实，社区使用 | dcgm-exporter |
| `msopgen` | 从算子信息 JSON 生成 Ascend C 算子工程骨架（tiling 逻辑需手写） | —（CUDA 无对应，算子直接写） |
| ATC | 图编译工具，ONNX → .om 离线模型 | trtexec |
