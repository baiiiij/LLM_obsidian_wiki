# 一次 flatten 的旅程

## 写在前面：这篇文章要回答什么问题

你写下一行代码：

```python
y = x.flatten(0, 1)   # 把 x 的第 0、1 维合并成一维
```

这行代码看起来简单到不能再简单。但它从 Python 出发，要穿过 **6 层代码**、经过 **十几次"该走哪条路"的判断**，才最终给你返回结果。这篇文章就把这条路完整走一遍，并且用大白话解释：

- 每一层是干什么的，为什么要有这一层；
- 每个岔路口（分支）往哪走、为什么这么走；
- 什么时候真的搬了数据、什么时候只是"改了个说法"；
- 哪些活是在 CPU 上干的、哪些活是在显卡（GPU）上干的。

# 第一部分：先补三个背景知识（不懂这些后面会迷路）

## 背景 1：一个张量 = 一块数据 + 一张说明书

PyTorch 里的张量（Tensor），内部其实是**两样东西分开存放**的：

1. **数据本体**：一大块内存，里面密密麻麻排着所有数字。比如一个 2×3×4 的张量，就是连续的 24 个浮点数。这块内存叫 **storage**（仓库）。
2. **说明书（元数据 / metadata）**：一张小纸条，写着"这批货该怎么看"：
   - **形状（sizes）**：几维、每维多长，比如 `[2, 3, 4]`；
   - **步长（strides）**：在某个维度上往前走一格，内存里要跳过几个数，比如 `[12, 4, 1]`；
   - **偏移量（offset）**：从数据块的第几个数开始算起。

用一个比喻：**数据本体是仓库里的一箱货，说明书是货架上的标签**。标签写"这批货是 2 排 × 3 列 × 4 层"，仓库管理员就知道怎么取货。

**关键点：同一箱货，可以换不同的标签。** 同样是 24 个连续的数字，标签写 `[2,3,4]` 就是三维张量，标签写 `[6,4]` 就是二维矩阵，标签写 `[24]` 就是一个长数组——**货一箱都没动**。

## 背景 2：view（换标签）和 copy（搬货）——全文最重要的一组概念

flatten 这种"改形状"的操作，有两种实现方式，差别巨大：

- **view（换标签）**：不动数据，新做一张标签贴在同一箱货上。代价 ≈ 0（就是写几个数字），速度极快。
- **copy（搬货）**：真的把 24 个数字抄到一块新内存里，再给新内存贴新标签。数据多大就搬多少，慢，还占双倍内存。

那什么时候能只换标签、什么时候必须搬货？**取决于新形状能不能用"旧说明书上的数字规律"表达出来。**

举个例子：`transpose`（交换两个维度）之后，数据在内存里的排列顺序其实没变，只是"看的顺序"变了，这时候标签上的步长不再是规则的。如果这时你要把交换过的两维合并成一维——对不起，没有任何一组"形状+步长"能描述这种看法，**只能老老实实把数据按新顺序重新抄一遍**。

一句话：**能换标签就换标签（view），换不了才搬货（copy）。flatten 的全部"决策"，就是在判断这件事。**

## 背景 3：PyTorch 为什么有个"总机"（dispatcher）

PyTorch 有 2000 多个操作（加减乘除、变形、卷积……），每个操作在不同情况下实现完全不同：

- 数据在 **CPU 内存**里，用一套代码；
- 数据在 **NVIDIA 显卡**里，用另一套代码；
- 如果这个张量"需要算梯度"（训练神经网络时），还要额外**记一笔账**：记下"这个 y 是从哪个 x 变来的"，以后反向传播要用。

问题来了：你写 `x.flatten()` 的时候，到底该执行哪份代码？**写代码的时候不知道，运行的时候才知道**（因为 x 在 CPU 还是 GPU、要不要梯度，是运行时才确定的）。

PyTorch 的解决办法是设一个"**总机 / 分诊台**"（官方叫 dispatcher）：

> 每个操作名都在总机那里登记了一本表：**操作名 → 一堆候选实现，每个实现标注了"我管什么情况"**。
> 每次调用，总机看一眼手里的张量"是什么来头"（在 CPU 还是 GPU？要不要梯度？），然后查表，把活派给对应的实现。

你可以把它想象成**医院分诊台**：病人（你的调用）来了，护士看一眼病历本（张量的属性），"内科三号诊室"——把人派过去。这个"看病例、派诊室"的动作，就叫 **dispatch（分派）**。

理解了这三点，后面就是观光旅游了。

# 第二部分：旅程总览——6 层，一张图

```
你在 Python 里写：x.flatten(0, 1)
│
├─ 第 0 层  Python 世界里找到"flatten 这个按钮"（在哪登记的？）
├─ 第 1 层  翻译官：把 Python 的参数翻译成 C++ 能懂的形式，然后放下"全局话筒"（GIL）
├─ 第 2 层  C++ 外壳：一行转发，把人送到总机
├─ 第 3 层  总机查表：看张量来头，连续过 4 道窗口，每道窗口盖一个章
├─ 第 4 层  干活的 flatten：纯心算，算出"新形状应该长什么样"
├─ 第 5 层  决策员 reshape：判断"能换标签吗？"
│     ├─ 能 → 换标签（view），完事，数据一个数字都没动
│     └─ 不能 → 先搬货（copy，全旅程唯一真干活的地方），再换标签
└─ 原路返回，把结果包装回 Python 对象交给你
```

下面一层一层说。

# 第三部分：逐层详解

## 第 0 层：Python 是怎么找到 "flatten" 这个按钮的

你打 `x.flatten`，Python 首先要回答：**`flatten` 这个方法定义在哪？**

答案可能出乎你的意料：**它不在任何 Python 文件里**。

PyTorch 有 2000 多个操作，如果每个都用 Python 手写一个方法，累死也维护不过来。所以 PyTorch 用了一个"**模板批量印刷**"的办法（官方叫代码生成）：

- 有一个总清单文件（`native_functions.yaml`），用几行字描述每个操作：名字叫什么、参数是什么、返回值是什么。flatten 在里面就两行；
- 编译 PyTorch 的时候，有个"印刷机"程序读这个清单，**自动批量生成**几千个方法的 Python 绑定代码（C 语言写的）；
- 这些生成的方法被装订成一本"方法名册"，挂在 `torch.Tensor` 这个类型上。

所以 `x.flatten` = Python 去 Tensor 类型的方法名册里查 "flatten"，找到一个 C 语言写的函数，跳过去。

> 顺便解释一个很多人踩过的坑：在 IDE 里对 `flatten` 按 F12 跳转，会跳到一个 `.pyi` 文件，里面只有类型声明、没有实现，是条死路。因为 `.pyi` 也是那台印刷机印的"给 IDE 看的假书"，真身在别处。

**这一层的开销**：就是查了个表，什么都没动。

## 第 1 层：翻译官（Python → C++ 的交接）

名册里那个 C 函数（内部叫 `THPVariable_flatten`）是个"翻译官"，它依次做 5 件事：

1. **拆包**：把 Python 的张量对象拆开，取出里面的 C++ 张量本体。就是读一个指针，几乎没有成本。
2. **解析参数**：你传的 `0, 1` 是 Python 的整数，要转成 C++ 的整数；你没传的参数（比如 `end_dim`）要填上默认值 `-1`。这里用的是一本"参数模板"（PythonArgParser），第一次用的时候构建一次，以后每次调用复用。
3. **检查"有没有人拦截"**：如果你有自定义的张量子类、重写了规则，这里会把调用转给你的 Python 代码。普通张量没有，直接过。**（分支点①）**
4. **放下"全局话筒"（GIL），然后正式调用 C++**：
   - Python 有个著名的全局锁（GIL），同一时刻只允许一个线程执行 Python 代码。
   - 翻译官在进 C++ 之前**主动把话筒放下**——因为后面 C++ 可能算很久，抱着话筒不放，其他 Python 线程全得干等。
   - 放下话筒后，调用 C++ 世界的 `self.flatten(0, 1)`。
5. **（等 C++ 返回后）重新拿起话筒，把 C++ 的结果包装回 Python 对象**：先看看这个结果张量是不是已经有对应的 Python 对象了（有就直接复用），没有就新造一个。

**内存操作**：全是 Python 对象层面的操作，没碰张量数据。**执行位置**：CPU（你的程序线程）。

## 第 2 层：C++ 外壳——一行转发

C++ 这边的 `self.flatten(...)` 也不是干活的，它也是个"壳"，整个函数体就一行：

```cpp
return at::_ops::flatten_using_ints::call(*this, start_dim, end_dim);
```

翻译成人话：**"这事不归我管，送总机。"**

（这个壳也是印刷机批量印出来的——2000 多个操作每个都有这么一个壳。）

## 第 3 层：总机查表（dispatcher）——连续过 4 道窗口

这是全旅程最"机关重重"的一层，但其实每个机关都有明确的目的。

### 3.1 总机先看张量的"来头"

总机拿到的第一件事，是算出这张调用单的"**来头标签集合**"：

- 张量自己身上带的：比如 "**CPU 张量**"、"**需要梯度功能**"（注意：这个标签**每个张量都贴着**，哪怕你不需要梯度）；
- 默认再加两个：一个叫"**view/inplace 特别服务窗口**"，一个叫"**设备确认窗口**"——这俩是每次调用都默认挂上的；
- 再减去一些"本次明确不要的服务"（比如没开自动混合精度，就去掉混合精度标签）。

算出来一堆标签后，**按优先级从高到低排**，优先级最高的那个标签，决定第一道窗口去哪。对一次普通的 flatten，优先级顺序是：

```
梯度记账窗口  >  view/inplace 特别服务窗口  >  设备确认窗口  >  具体干活的窗口
```

### 3.2 第 1 道窗口：梯度记账（VariableType）

**每个操作都要先过这扇窗，无一例外**（哪怕你不需要梯度）。

窗口里的职员看一眼："这张量需要记账吗？"

- **不需要**（我们这次的情况）：什么也不记，但他会做一件重要的事——在单子上盖一个"**梯度窗口已办**"的章，然后把单子转给下一窗口。
- 需要：把"输出是从哪个输入、经过什么变换来的"记到账本上（反向传播时用），再盖章转交。

这个"盖章"是有实际作用的：**章一盖，后面的流程就不会再绕回这个窗口**。不然 flatten 内部再调用别的操作时，会重复记账，账就乱了。（记住这个章，它是理解"为什么 reshape 不重新排队"的钥匙。）

### 3.3 第 2 道窗口：view/inplace 特别服务（ADInplaceOrView）

这扇窗**只有"改形状/原地改值"这类操作才有**——因为它们有特殊的记账需求："y 和 x 共用一箱货"这件事，账本上要用专门的方式记录。

对我们这次（不需要梯度）：职员同样只是看一眼，盖"**已办**"的章，转交下一窗口。

### 3.4 第 3 道窗口：设备确认（BackendSelect）

职员核对："单子说去 CPU 窗口办，张量确实是 CPU 张量，没填错。"如果是 GPU 算子，这里还会做"切换到正确的显卡"的动作。核对完，转交。

### 3.5 第 4 道窗口：终于到干活的——可是 flatten 没有"CPU 专属窗口"

按照剧本，这里该到"CPU 实现窗口"了。但查表一看：**flatten 压根没有为 CPU 或 GPU 单独注册实现！**

为什么？因为 flatten 干的活是**纯心算**（算几个整数的乘积、拼一个新形状），**跟数据在 CPU 还是 GPU 一点关系都没有**——同一套逻辑到处通用。既然通用，就没必要给每个设备单独写一份，PyTorch 给它注册的是一个"**全科窗口**"（官方叫 CompositeImplicitAutograd）：什么情况都能看。

于是单子被转进全科窗口，窗口里坐着真正的 flatten 本体。**四道窗口过完，"总机之旅"结束。**

> 这 4 道窗口听起来繁琐，但每一道都只做几个判断，纳秒级开销。换来的是：2000 多个操作自动获得"梯度记账、view 追踪、设备检查"三件套，不用每个操作手写——这就是总机存在的意义。

## 第 4 层：flatten 本体——纯心算，不碰数据

flatten 的真正实现（`TensorShape.cpp` 里的 `at::native::flatten`）做的事简单到令人发指，还带有几个"偷懒"分支：

```cpp
Tensor flatten(self, start_dim, end_dim) {
    start_dim = 把负数维度转正;   // 比如 -1 意思是"最后一维"     【分支②】
    end_dim   = 把负数维度转正;
    if (start_dim > end_dim) 报错;                              【分支③】

    if (x 是 0 维标量)        return x.reshape({1});            【分支④：变成长度 1 的数组】
    if (start_dim == end_dim) return x;                         【分支⑤：只"合并"一维 = 啥也没干，原样返回】

    新形状 = 前几维不变 + [中间几维的乘积] + 后几维不变;          // 比如 [2,3,4] 合并 0~1 维 → [6,4]

    return reshape(x, 新形状);      // ★ 注意：这里直接喊 reshape 的名字，没有回总机排队！
}
```

看到了吗——**flatten 自己根本不做 view/copy 的判断**，它唯一的职责是"算出目标形状"，然后把球传给 reshape。

**执行位置**：CPU。**内存操作**：就是拼了一个装有几个整数的小数组（新形状）。**数据**：一个数字都没碰。

### 重点解答：为什么这里直接喊 reshape 的名字，不回总机重新排队？

这就是很多人困惑的"**为什么 reshape 没有走注册/分派，而是被直接调用**"。三个原因：

1. **reshape 这部分活也是纯心算，跟设备无关。** 回总机排队的唯一意义是"让总机根据情况挑实现"，可 reshape 的"判断能不能换标签"这套逻辑在 CPU、GPU 上一模一样——挑无可挑，排队纯属浪费。

2. **该盖的章已经盖过了。** 还记得第 3 层那几道窗口盖的章吗？梯度记账、view 追踪，flatten 进来时已经办完了。reshape 是 flatten 的"内部同事"，如果让它重新排队，它会被当成一个**全新的独立调用**再过一遍那几道窗口——**同一笔账记两次**，账本直接错乱。

3. **省开销。** 总机查表虽然快（纳秒级），但 flatten 这种高频小操作，能省一次是一次。

用医院比喻：**你（flatten）已经在分诊台挂完号、盖完章、进了内科。内科医生让同科室的 reshape 护士帮个忙，是直接喊一嗓子，而不是让护士重新去大厅排队挂号。**

那什么时候**必须**回总机？当要干的活**真的因设备而异**的时候——比如马上要讲到的"搬货"（copy）：CPU 搬货用 CPU 的办法，GPU 搬货用 GPU 的办法，这种就必须回总机分派。

## 第 5 层：reshape——换标签还是搬货的"决策员"

reshape 拿到 flatten 算好的新形状，开始按流程判断：

```
if (x 是稀疏张量)           报错，不支持                        【分支⑥】
if (x 在内存里是"标准连续排列") {
    return 直接换标签;                                        【分支⑦：快通道，必能换】
}
新形状 = 补全推导（处理 -1 这种"你自己算"的写法）;
新步长 = computeStride(旧形状, 旧步长, 新形状);   // ★ 核心判断算法
if (新步长算出来了) {
    return 换标签（用算好的新步长）;                            【分支⑨】
} else {
    新货 = 把数据按标准顺序搬一箱新的;      // ★★ 全旅程唯一真搬数据的地方
    return 给新货贴新标签;                                      【分支⑪】
}
```

### 5.1 核心判断算法 computeStride 在干什么

它回答的问题用一句话说：**"新形状能不能只用一张新标签表达，不动数据？"**

它的做法像玩拼图：

- 把旧形状从后往前切成若干"**连续块**"——块内的维度在内存里是严丝合缝挨着的（比如 `[2,3,4]` 标准排列时，3 和 4 这两维就是一整块）；
- 然后尝试用新形状的末尾几维，**恰好严丝合缝地填满每一旧块**；
- 每一块都填得上 → 能换标签，顺便把新标签上的步长算好了；有任何一块填不上 → 换不了，只能搬货。

对应到 flatten 的场景，结论非常直白：

> **你要合并的那几维，如果在内存里本来就是挨着的（或者其中有长度为 0 或 1 的维），就只换标签；否则搬货。**
> 常见的"标准排列"张量必然只换标签；`transpose` 之后再合并被交换的两维，必然搬货。

### 5.2 "换标签"具体换了什么

换标签的实现（`alias_with_sizes_and_strides`）做的事，逐条列出来：

1. 新造一张标签（一个新的小对象，里面装形状、步长、偏移量——加起来几百字节）；
2. 标签上"数据本体"那一栏，**直接填原来那箱货的地址**，并把仓库的"借用计数"加 1（表示现在有两张标签指着这箱货）；
3. 完事。

**数据本体：一个数字都没动。** 不管你的张量在 CPU 内存还是显卡显存里，这一步**都发生在 CPU 上、纯写几个数字，连一次 GPU 调用都没有**。这就是为什么 view 操作几乎零成本。

### 5.3 "搬货"具体怎么搬的（全旅程唯一真干活的分支）

搬货分两步：**先申请一块新地方（empty_like），再真的搬（copy_）**。

**第一步：申请新地方。**
- CPU 张量：在内存里 `malloc` 一块新的；
- GPU 张量：找显存管理员要一块——管理员有个"回收池"，优先从池子里拿以前用过还回来的块，池子没有才真正问显卡驱动要（cudaMalloc）。
- 注意：就算申请的是显存，"申请"这个动作本身也是 CPU 在记账，没有启动任何 GPU 计算。

**第二步：copy_ 真搬。** 这活**因设备而异**，所以必须回总机分派（这就是"什么时候必须回总机"的活例子）：

- **CPU 搬 CPU**：用向量指令成批地抄，数据大的话还会多线程分工抄。源数据如果不连续（比如 transpose 过），就按标签上的步长跳着抄；
- **GPU 搬 GPU**（同一张卡）：
  - 如果源和目标都是连续的、类型也一样 → 直接调 `cudaMemcpyAsync`（显卡自己的高速整块拷贝）；
  - 如果不连续（flatten 搬货正是这种情况：源是 transpose 过的）→ **启动一个 GPU 小程序（kernel）**：几万个线程一人抄一个数，每个线程按步长算出自己该去哪读、写到哪。**这是整个 flatten 旅程里唯一一次真正在显卡上跑计算**；
- **CPU 和 GPU 之间搬**：走 `cudaMemcpyAsync` 跨设备拷贝。

搬完之后，得到一箱**排列标准**的新数据，最后一步：给它贴上 flatten 想要的新形状标签（这里用的是一个"内部免记账"的贴标签通道，因为这箱新货是临时产物，它的账记在 clone 头上就够了）。

**所以"搬货"分支的全貌是**：CPU 上申请新内存 → **设备上**真搬数据（全旅程唯一碰数据、唯一可能用到 GPU 的地方）→ CPU 上贴新标签。

## 第 6 层：原路返回

结果沿着来路一层层退回去：各窗口把之前盖过章的单子收回存档 → 回到翻译官那里 → 重新拿起 GIL 话筒 → 包装成 Python 对象 → 交到你的变量 `y` 手里。

# 第四部分：三张总结表

## 表 1：分支大全——每个岔路口往哪走

| # | 岔路口 | 条件 | 去向 |
|---|---|---|---|
| ① | 翻译官 | 有自定义子类拦截 | 转去执行你的 Python 代码 |
| ② | flatten | 维度写越界了 | 报错 |
| ③ | flatten | start_dim > end_dim | 报错 |
| ④ | flatten | x 是 0 维标量 | 变成长度 1 的数组 |
| ⑤ | flatten | 只"合并"单独一维 | 啥也没变，原样返回（零成本） |
| ⑥ | reshape | 稀疏张量 | 报错 |
| ⑦ | reshape | 内存里标准连续 | **快通道：直接换标签** |
| ⑨ | reshape | 算法判断新形状能用旧规律表达 | **换标签** |
| ⑪ | reshape | 表达不了 | **搬货 + 贴标签**（唯一真干活） |
| ⑫ | 搬货 | CPU↔GPU 且不连续/要转类型 | 先整理成连续的临时货再搬 |
| ⑬ | 搬货（同卡） | 两边都连续同类型 | 整块高速拷贝；否则启动 GPU 小程序逐元素搬 |

## 表 2：每一步在哪干、动不动数据

| 步骤 | 在哪执行 | 动不动数据 |
|---|---|---|
| Python 找方法 | CPU | 不动 |
| 翻译官（解析参数、放话筒） | CPU | 不动 |
| 总机四道窗口 | CPU | 不动（需要梯度时会在 CPU 上记账） |
| flatten 算新形状 | CPU | 不动 |
| computeStride 判断 | CPU | 不动 |
| **换标签** | CPU | **不动，GPU 完全无感** |
| 搬货·申请新内存 | CPU 记账 | 新占一块内存/显存 |
| **搬货·copy_** | **设备上**（CPU 搬运 / GPU 小程序或高速拷贝） | **动了！全程唯一** |
| 贴新标签、包装返回 | CPU | 不动 |

## 表 3：快问快答

**Q：flatten 会复制我的数据吗？**
A：看你合并的维度在内存里是否连续。标准张量（没 transpose/切片折腾过）→ 不复制；`transpose` 后合并被交换的维度 → 复制。验证方法：`y._base is x` 为 True 就是没复制。

**Q：GPU 张量做 flatten，GPU 会干活吗？**
A：换标签的情况下 GPU 一下都不动，全程是 CPU 在改几个数字；只有搬货的情况，GPU 才会真正跑一个拷贝程序。

**Q：为什么 flatten 不给 CPU/GPU 分别注册实现？**
A：因为它的活（算形状）是纯整数心算，跟设备无关，一份代码全通用——注册成"全科"就够了。

**Q：为什么 flatten 内部叫 reshape 帮忙时不回总机排队？**
A：reshape 的活也跟设备无关，排队没意义；而且 flatten 进来时该盖的章（梯度记账、view 追踪）都盖过了，reshape 重新排队会被重复记账。科室内部直接喊人，不回大厅挂号。

**Q：那什么操作必须回总机？**
A：做法**真的因情况而异**的操作。典型就是搬货（copy_）：CPU 搬和 GPU 搬是两套完全不同的代码，必须让总机按张量来头分派。

**Q：这 6 层、4 道窗口，会不会很慢？**
A：每层都是几个判断和指针操作，总开销纳秒级。换来的是 2000+ 操作自动获得梯度记账、view 追踪、设备检查三件套，以及第三方库能在运行时不改一行 PyTorch 代码就替换掉某个操作的实现——这套机制是 PyTorch 可扩展性的地基。

# 第五部分：一句话带走

> **flatten 自己不干活，它只是算出"新形状"，然后让 reshape 判断：能用新标签描述就只换标签（零成本，GPU 无感），描述不了才真的把数据搬一遍（全旅程唯一动数据、唯一可能用到 GPU 的地方）。而在到达 flatten 之前，你的调用已经在总机那里盖完了梯度、view、设备三个章——这就是 PyTorch 所有 2000 多个操作每天重复的旅程。**
