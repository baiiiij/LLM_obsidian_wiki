# PyTorch 代码生成管线

PyTorch 有 2000+ 算子，每个都要配 Python 绑定、C++ 方法、autograd、各后端 kernel、类型存根——全手写不可维护，于是采用 **schema 驱动代码生成**：`aten/src/ATen/native/native_functions.yaml` 是唯一事实来源，build 期由生成器批量产出各层代码。本页是"哪个文件由谁生成、生成到哪"的参考地图。

> 配套页面：[[PyTorch-ATen-Dispatcher]]（生成产物运行时的路由机制）；[[aten算子调用链定位方法论]]（用这张地图走查任意算子的 SOP）；[[pytorch-flatten-调用链路定位]]（flatten 实例）。

## 三个世界：文件的归属分类

看 PyTorch 源码最大的困惑是"文件到底在哪"。其实只有三类：

| 世界 | 说明 | 例子 |
|---|---|---|
| ① 源码自带 | git clone 就有，直接可读 | `aten/src/ATen/native/TensorShape.cpp`、`tools/autograd/gen_python_functions.py` |
| ② build 生成·写回源码树 | 编译时生成，但落在源码目录里 | `torch/_C/__init__.pyi`、`torch/csrc/autograd/generated/` |
| ③ build 生成·落在 build/ | 编译时生成，只在 build 目录 | `build/aten/src/ATen/ops/flatten.h`、`build/aten/src/ATen/Register*.cpp` |

**IDE 点跳转到 `.pyi` 是死路**，因为它属于世界②——`tools/pyi/gen_pyi.py` 生成的纯类型存根，只服务 IDE 补全，从来不含实现。build 产物的安装目录由 `cmake/Codegen.cmake` 的 `--install_dir ${CMAKE_BINARY_DIR}/aten/src/ATen` 决定。

**通用判别动作：生成的文件自己会报出生。** 每个生成文件的头注释都写着 `@generated by {生成器} from {模板}`——拿到任何一个文件，先看头注释就知道它在地图里的位置。

## 唯一输入：native_functions.yaml 的关键字段

每个算子条目里影响代码生成的字段：

| 字段 | 作用 |
|---|---|
| `func: op.overload(参数签名)` | schema；overload 名（点号后）只是 codegen 内部标识，调用方按**参数类型**匹配 |
| `variants: function, method` | `function` ⇒ 生成 `torch.op(...)` 绑定；`method` ⇒ 生成 `t.op(...)` 绑定（都写就都有） |
| `python_module: nn`（可选） | 绑定进 `torch._C._nn` 而非顶层 `torch`（linalg/fft/sparse/special 同理） |
| `dispatch: CPU: foo_cpu / CUDA: foo_cuda` | 每后端独立 kernel（决定 Register{Key}.cpp 的注册内容） |
| 无 `dispatch:` 段 | 默认 CompositeImplicitAutograd：一份 C++ 实现服务所有后端 |
| `structured_delegate: bar` | meta 算 shape 后整体委托另一算子（旧版 flatten 曾用，2.12 已改直接实现） |
| `device_check` / `device_guard` | 控制生成 wrapper 里的设备检查/DeviceGuard 代码 |

> 注意版本漂移：同名算子在不同版本的 yaml 形态可能不同，以本地源码树为准。

## 三个生成器及其产物

| 生成器（源码自带） | 产物（build 生成） | 内容 |
|---|---|---|
| `torchgen/gen.py` | `build/aten/src/ATen/ops/{op}_ops.h` 等 per-op 头文件 | `at::_ops::{op}` 结构体（`call`/`redispatch`，body = 查表） |
| 〃 | `build/aten/src/ATen/Functions.h/.cpp` | `at::{op}(...)` 命名空间函数 |
| 〃 | `build/aten/src/ATen/core/TensorBody.h` + `TensorMethods.cpp` | `Tensor::{op}(...)` 方法 |
| 〃 | `build/aten/src/ATen/Register{CPU,CUDA,CompositeImplicitAutograd,...}.cpp` | **注册表项** `m.impl("aten::{op}", TORCH_FN(kernel))`（格式见 gen.py:1042） |
| `tools/autograd/gen_python_functions.py` | `torch/csrc/autograd/generated/python_variable_methods.cpp` | `THPVariable_{op}`（**tensor 方法**绑定） |
| 〃 | `torch/csrc/autograd/generated/python_torch_functions.cpp` | `torch.{op}` 绑定（**命名空间函数**） |
| 〃 | `torch/csrc/autograd/generated/python_nn_functions.cpp`（及 linalg/fft/sparse/special/nested） | `torch._C._nn.{op}` 等分模块绑定 |
| `tools/autograd/gen_autograd.py` | `torch/csrc/autograd/generated/VariableType*.cpp`、`ADInplaceOrViewType*.cpp` | Autograd/ADInplaceOrView key 的包装 kernel（记 backward/view） |
| `tools/pyi/gen_pyi.py` | `torch/_C/__init__.pyi` | 类型存根（IDE 用，**死路**） |

模板都在源码树里：C++ 侧 `aten/src/ATen/templates/*.h/.cpp`（`Operator.h`、`Function.h`、`TensorBody.h` 等），Python 绑定侧 `tools/autograd/templates/*.cpp`（`python_variable_methods.cpp`、`python_torch_functions.cpp`、`VariableType.cpp` 等，文件里的 `${py_methods}` 占位符就是模板身份的证明）。

**挂载点**（生成的表怎么变成可调用的属性）：

- `t.op` → `torch/csrc/autograd/python_variable.cpp:3887` `extern PyMethodDef variable_methods[]`，挂到 `torch._C.TensorBase` 类型；
- `torch.op` → `torch/csrc/autograd/python_torch_functions_manual.cpp:539+` `gatherTorchFunctions_0/1/2()` 汇总生成的分片表，挂到 `torch` 模块。

## 拿到新算子，找哪个绑定文件？（判定规则）

规则原文在 `gen_python_functions.py:233-237`：`is_method = python_module is None and Variant.method in variants`。按调用形式查表：

| 你写的调用形式 | 先查 | 落点 |
|---|---|---|
| `t.op(...)` | yaml 有 `variants: ..., method` | `python_variable_methods.cpp` 的 `THPVariable_op` |
| `torch.op(...)` | yaml 有 `variants: function` | `python_torch_functions.cpp` |
| `torch.nn.functional.op(...)` / `F.op` | `torch/nn/functional.py` 有 **Python 包装**（getsource 可读！） | 包装内部调 `torch._C._nn.op` → `python_nn_functions.cpp`（yaml 里 `python_module: nn`） |
| `torch.linalg/fft/sparse/special.op` | 同上 | 对应 `python_{linalg,fft,sparse,special}_functions.cpp` |
| `torch.save` / `torch.compile` / `torch.utils.*` | **不是 aten 算子**，yaml 里搜不到 | 纯 Python（`torch/*.py`），`inspect.getsource` 直接可读 |

## Register 文件：三件套与分片

每个 `Register{Key}.cpp` 里都是 torchgen 为每个 (op, key) 对生成的**标准三件套**：

```cpp
// ① anonymous namespace 里的 wrapper：加设备检查/DeviceGuard 后调 kernel
//    （注释内容对应 yaml 的 device_check / device_guard 字段）
at::Tensor wrapper_CompositeImplicitAutograd_using_ints_flatten(...) {
  return at::native::flatten(self, start_dim, end_dim);
}
// ② 静态初始化注册块：import torch 时执行，把表项写进全局表
TORCH_LIBRARY_IMPL(aten, CompositeImplicitAutograd, m) {
    // ③ 绑定：算子名 → wrapper 函数指针
    m.impl("flatten.using_ints", TORCH_FN(wrapper_...));
}
```

**分片**：大文件会切片以便并行编译（torchgen gen.py:2376-2384：`RegisterCPU` 切 4 片 `RegisterCPU_0~3.cpp`，`CompositeImplicitAutograd` 1 片）。**同一个 (op, key) 的 wrapper 只出现一次**——若同一 wrapper 出现在多个文件，用 `rg -l` 列出文件名诊断（大概率是多个 build 目录）。

## 无 build 时的实证：pip 版自带头文件

pip 安装的 torch 自带 `torch/include/ATen/ops/*.h` 生成头文件，无需编译即可实证包装层：

- `{op}.h`（`@generated by torchgen/gen.py from Function.h`）：`at::{op}()` 的整个 body 就是一行 `return at::_ops::{op}_{overload}::call(...)`；
- `{op}_ops.h`（`@generated from Operator.h`）：`_ops::{op}` 结构体，内含完整 `schema_str`；
- `{op}_{key}_dispatch.h`（如 `flatten_compositeimplicitautograd_dispatch.h`）：旁证该 op 注册在哪个 dispatch key 下。

定位：`python -c "import torch, os; print(os.path.dirname(torch.__file__))"` → `include/ATen/ops/`。
